# 雨夜操作與演出修正

本輪取代 16e7d75 的平板演出；後台 API、D1 結構、照片三按鈕、八題課程與通關玩法沿用。

## 操作與效能

- 暫停回右上；暫停／背景恢復使用原對話區的大按鈕，這次點擊不推進台詞或觸發節奏。
- 中斷節奏會取消當前小段、解除長按，保留已完成段數；重開不增加失敗、不重複生物。
- 移除最後一擊每幀 0.05 秒上限，低幀率不再因此累積慢動作。
- 充能時提前編譯發射及瓦礫材質，並在 128×128 的隱藏渲染目標，以非零實例及無遮擋的材質網格先跑過實際繪製。主場景物件不移動，分別準備正式 MSAA 與反射繪製路徑，另用獨立小型陰影貼圖準備深度繪製；渲染目標及陰影更新設定在 finally 還原；過程顯示準備提示。
- 倒塌光源固定在原位置，熄燈改成亮度為零，避免因父物件隱藏改變整批材質的光源數量；回放及復原恢復原亮度。實際店面測試光源數為 10 → 10，最後伺服器熄燈同樣維持數量。
- 自動畫質在戰鬥、最後一擊、節奏及房子演出時延後重建解析度／抗鋸齒／陰影等資源，只先降低特效預算。手動畫質照使用者選擇。
- 可見長幀會納入降畫質判斷；載入／背景／暫停不作為效能樣本。診斷幀時間於初次載入完成後重新開始記錄。

發射頁、一般砲擊、最後一擊及落地期間鎖定演出鏡頭，隱藏並停用視角選擇、清除拖曳慣性。人物使用跟隨角色位移的保守裁切範圍，每個渲染相機獨立判斷是否繪製；不以可見性停止碰撞、倒塌或劇情更新。

## 塞西回放

1. 冰沙與氣泡水 → 冰箱不夠冰 → 越肩靠近平板；首屏只有搜尋漏洞。
2. 精簡 PHP2Shell／RCE／CVSS 9.2／CVE-2026-109618 資訊；角色台詞獨立使用正式對話框。
3. 實際走過通道到冰箱，站穩才開放套用；溫度在四秒除霜演出中從 +4°C 升至 +50°C。
4. 門框控制面板與燈條警示保留商品層次；開門、取出梨花水、對話、放到旁邊後才回微波爐。
5. 3 號天師樁有實體維護控制台，妮姬啟動器使用拉毗角色圖。電線循牆邊接至微波爐側面插座，來源／街道／設備三段鏡頭使用同一股能量進度。
6. 800 W 可按且被拒絕，800 MW 要另行確認，供電接通不代表已開始加熱。

平板改為穩定持握，持握解只需建立一次；取飲料時才更新伸手。閱讀鏡頭對齊螢幕方向，減少斜字與頭髮遮擋。熱冰箱為主線開場的既定狀態；三小時前回放才先顯示正常冷藏，返回現場及重開仍為過熱狀態。

## 驗證與限制

- 34 組 Node 檢查涵蓋既有故事、相機、街道、賽車、回饋，以及新增平板關卡、實際品質切換入口與冰箱時間線。
- `scripts/vcr-browser-check.py` 使用 Chromium SwiftShader，驗證實體平板點擊、直橫向構圖、逐句對話、走到冰箱、溫度上升、妮姬圖載入、三段電線、功率分支、十次模擬背景中斷及最後發射。
- 背景中斷驗收透過受控 visibilitychange 事件；不是 iOS 作業系統鎖屏實測。
- 軟體 WebGL 的渲染呼叫耗時只用於同環境對照，不代表 iPhone GPU FPS。實機流暢度、Safari 真實 App 切換與記憶體壓力仍需真機驗收。

同環境逐幀對照（390×844、低畫質、SwiftShader，每次繪製間隔兩個 requestAnimationFrame；基準為平板改動前的 fb0e422）：

| 測量 | 基準 | 修正後 |
| --- | ---: | ---: |
| 一般三次砲擊，最長繪製呼叫 | 4428.2 ms | 102.9 ms |
| 一般砲擊，p95 | 79.4 ms | 55.0 ms |
| 最後一擊，最長繪製呼叫 | 2355.9 ms | 55.0 ms |
| 最後一擊，p95 | 35.5 ms | 29.9 ms |
| 擷取幀三角形數 | 105788 | 26148 |

這是渲染呼叫耗時及單幀幾何量的診斷，沒有量到真實手機的 GPU 完成時間。測試必須逐幀排程，不能在同一個 JavaScript 工作中連續提交大量渲染，避免將 GPU 排隊誤判為遊戲停頓。
