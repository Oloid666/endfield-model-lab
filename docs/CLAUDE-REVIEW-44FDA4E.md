## P2：Claude 觀察與本地核對

`src/world.js:166–190`確認有兩次獨立視角的composer render：全景長邊2048（直屏尺寸由aspect決定），有效人臉時另拍1536×1920近照，兩張均`toDataURL('image/png')`。無有效人臉時不產生近照。手機上的縮圖仍由本次全景canvas製作。

Claude 實測回傳data URL：全景2.21MB、近照2.87MB，共5.08MB。合成圖JPEG 0.86測試：2.98→0.29MB、3.63→0.31MB；編碼79→30ms、113→36ms。**這些是Claude提供的測試結果，合成圖比例不能直接當作本遊戲照片的保證。**

建議實作：

1. 先只換JPEG 0.86，維持兩張原尺寸、同一凍結角色姿勢與原有全景／光學近照關係，不改第一張照片內容或有效人臉判斷。
2. 在真實全景、人物近照、無臉照片三種情境量字串大小與編碼耗時；壓縮碼率影響文字／眼睛邊緣，要用實際圖驗證。
3. 再比較1024×1280近照與原1536×1920（像素數下降約55.6%）。以目前相簿顯示、縮放上限及實際裝置DPR檢查，能判斷眨眼才採用；若不清楚則保留較高解析度，調整編碼預算，不能為達數字犧牲可辨識性。
4. 重拍、相簿切換、傳送、切出返回、取消拍攝、重開與例外後，檢查相機／renderer/composer尺寸與輸入均恢復，舊照片及貼圖沒有持續累積。
5. 保留現有data URL介面，不為這輪立即改Blob URL而增加非同步、URL回收及相簿生命週期風險。若之後記憶體量測顯示仍需要，再獨立規劃。

**記憶體界線：** base64字串大小不是瀏覽器總記憶體；解碼圖片、canvas、GPU render target與composer多個buffer也占空間。JPEG主要減少編碼資料，降低近照尺寸才會減少對應像素buffer；兩者均須量測，不先宣稱iPhone記憶體或FPS已改善。Claude報告的54.7秒拍照來自SwiftShader軟體渲染，不作手機數字。
